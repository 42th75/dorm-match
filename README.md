# 기숙사 룸메이트 배정

설문 응답으로 2인실 룸메이트를 자동 배정하는 웹 사이트.
서버 없이 정적 파일만으로 돌아가서 깃허브 페이지에 그대로 올라간다.

**처음이라면 [START.md](START.md) 를 순서대로 따라간다.**

---

## 무엇을 하는가

1. 구글 폼 응답(CSV)을 붙여넣으면 어느 열이 무슨 문항인지 자동으로 알아본다
2. 생활 습관에서 **비대칭 생활비용**을 만든다 — A가 B와 지내는 불편함과 그 반대가 다르다
3. 전체 생활차이를 줄이되 **가장 힘든 학생 한 명을 특히 강하게 보정하는** 배정을 찾는다
4. 결과 파일 하나만 커밋하면 학생들이 학번으로 자기 방을 확인한다

## 권한

| | 학생 | 관리자 |
|---|---|---|
| 학번으로 내 방 확인 | O | O |
| 전체 방 목록 | O | O |
| 응답 불러오기 | X | O |
| 배정 실행·공개 | X | O |

비밀번호는 `js/config.js` 에 있다. 정적 사이트라 숨겨지지 않는다.
실수를 막는 잠금이지 보안 장치가 아니며, 실제 권한은 저장소에 push 할 수 있는 사람에게 있다.

## 개인정보

- **설문 원본과 기피 학번은 관리자 브라우저에만 저장된다.** 저장소에 올라가지 않는다
- 공개되는 `data/result.json` 에는 방 목록과 짧은 근거만 들어간다
- 기피는 한쪽만 적어도 양쪽에서 제외되고, 배정 근거 문구에도 나타나지 않는다

## 설문 문항

| # | 질문 | 형식 |
|---|---|---|
| 1 | 학번 | 단답 |
| 2 | 이름 | 단답 |
| 3 | 평일에 보통 몇 시에 잠드나요? | 24시 이전 / 24:00–00:30 / 00:30–01:00 / 01:00–01:30 / 01:30–02:00 / 02시 이후 |
| 4 | 평일에 보통 몇 시에 일어나나요? | 7시 이전 / 7:00–7:20 / 7:20–7:40 / 7:40–8:00 / 8시 이후 |
| 5 | 옆에서 나는 작은 소리나 불빛 때문에 잠을 설치나요? | 1~5 |
| 6 | 책상이나 바닥에 물건이 며칠씩 쌓여 있는 편인가요? | 1~5 |
| 7 | 잘 때 방 온도는 어느 쪽이 좋나요? | 1~5 |
| 8 | 룸메이트를 정할 때 가장 중요한 것 하나를 고른다면? | 취침·기상 시간 / 방의 조용함 / 정리 정돈 / 방 온도 / 상관없음 |
| 9 | 같은 방이 되면 곤란한 학생이 있나요? (학번만) | 단답, 선택 |

문항은 **성향이 아니라 행동**을 묻는다. "깔끔한 편인가요"라고 물으면 대부분 그렇다고 답해
아무도 구분되지 않지만, "물건이 며칠씩 쌓여 있나요"라고 물으면 실제로 갈린다.

취침·기상 보기는 12시 이후 취침, 7시 이후 기상이라는 우리 기숙사 사정에 맞춰 좁게 잡았다.
규정이 바뀌면 `js/matcher.js` 의 `FIELDS` 에서 보기와 숫자를 같이 고친다.

## 알고리즘

### 비대칭 생활비용

A가 B와 지내는 불편함과, B가 A와 지내는 불편함은 같지 않다. 잠귀가 밝은 학생에게
한 시간 늦게 자는 룸메는 매일 밤이 괴롭지만, 둔감한 학생에게는 같은 차이가 별일이 아니다.
그래서 민감도를 **자기 쪽 값만** 써서 시간 차이에 곱한다.

```
비용(A→B) = 가중치 × |A취침 − B취침| × (A의 민감도 배율)
          + 가중치 × |A기상 − B기상| × (A의 민감도 배율)
          + 가중치 × |정리 차이| + 가중치 × |온도 차이|
```

'가장 중요한 것'으로 고른 항목은 그 학생에게만 가중치를 두 배로 준다.
문항 하나로 개인별 맞춤이 되니 설문을 늘리지 않아도 된다.

취침 범위가 24시~02시로 좁아졌으므로 정규화 기준도 같이 줄였다(취침 1.5시간, 기상 0.8시간).
안 그러면 30분 차이가 거의 0으로 뭉개져 변별력이 사라진다.

### 배정 목표

```
점수 = 전체 생활차이의 합 + 1.5 × 인원 × (가장 큰 개인 생활차이)
```

이 점수가 가장 낮아지는 배정을 2-교환 국소 탐색으로 찾는다. 출발점은 여럿을 쓰는데,
그중 하나가 아래 Irving 알고리즘의 답이다.

### 왜 안정 배정을 최종안으로 쓰지 않는가

이 문제의 고전 해법은 **Irving 안정 룸메이트 알고리즘**이다. 서로 지금 룸메보다 상대를
더 좋아하는 쌍(차단 쌍)이 하나도 없는 배정을 찾고, 그런 배정이 존재하지 않으면
존재하지 않는다는 것까지 증명한다. 이 프로그램에도 구현돼 있고 출발점으로 쓰인다.

그런데 실제로 돌려 보니 차단 쌍을 0으로 만드는 대가가 컸다. 80명 24회 실측이다.

| 방식 | 차단 쌍 | 평균 순위 | 생활차이 큰 학생 | 아주 큰 학생 |
|---|---|---|---|---|
| 안정 우선 (Irving) | 1.0 | 4.40 | 7.8명 | **2.7명** |
| 이 프로그램 | 22.2 | 3.10 | **3.5명** | **0.0명** |

안정 우선은 매년 평균 2.7명이 심하게 안 맞는 방에 배정된다. 차단 쌍을 없애려다
한 학생을 아주 나쁜 상대와 묶는 일이 잦기 때문이다.

차단 쌍이 실제 문제가 되려면 두 학생이 **서로의 설문 응답을 알아야** 한다. 학생들은
그걸 모르니 이론적 지표에 가깝다. 반면 "룸메랑 생활 패턴이 안 맞는다"는 실제로 나오는
민원이다. 그래서 실제 불편을 줄이는 쪽을 골랐다.

### 희망 룸메를 받지 않는 이유

처음에는 희망 룸메도 받으려 했다. 그런데 희망을 받으면 A는 B를, B는 C를, C는 A를
원하는 순환이 자주 생겨 좋은 배정 자체가 어려워진다. 안정 배정 존재율이
65%에서 35%로 떨어졌다. 그래서 받지 않는다.

### 검증

Irving 알고리즘은 회전 제거 부분이 까다로워 눈으로는 맞는지 알 수 없다. 그래서
4·6·8명 규모에서 **가능한 모든 짝짓기를 전부 만들어** 안정적인 것을 직접 골라낸 뒤
알고리즘 결과와 대조했다. 3,400회 전부 일치했고, 안정 배정이 존재하지 않는 186건도
빠짐없이 '없다'고 판정했다.

### 홀수일 때

이 기숙사는 2인실만 있으므로 3인실을 만들지 않는다. 응답이 홀수면 한 명이 남고,
남은 학생은 혼자 쓰는 방으로 둔다. 배정 화면과 학생 조회에 그렇게 표시되니,
관리자가 응답 인원을 짝수로 맞춰 다시 배정한다.

## 파일 구성

```
.
├── index.html          화면 구조
├── css/style.css       스타일
├── js/config.js        제목·비밀번호            ← 보통 여기만 고친다
├── js/matcher.js       배정 엔진 (화면과 무관한 순수 계산)
├── js/csv.js           구글 폼 CSV 읽기, 열 자동 인식
├── js/store.js         자료 보관과 권한
├── js/ui.js            화면 그리기
└── data/result.json    공개되는 배정 결과       ← 배정할 때마다 갈아끼운다
```

`js/matcher.js` 는 DOM을 전혀 건드리지 않아서 Node에서 바로 불러 쓸 수 있다.
가중치를 바꾸거나 다른 방식과 비교해 보려면 여기만 보면 된다.

## 자주 손보는 것

- **가중치** — `js/matcher.js` 의 `BASE_W`
- **가장 힘든 학생을 얼마나 챙길지** — 같은 파일의 `WORST_W` (크게 할수록 평균을 희생해서 한 명을 구한다)
- **'생활차이 큼' 기준** — 같은 파일의 `HARD`, `VERY_HARD`
- **설문 보기와 열 찾기 낱말** — 같은 파일의 `FIELDS`
